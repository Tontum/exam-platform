# 10 - 高频问题与回答

> 本文档汇总教师培训在线考试系统在设计、开发和面试中可能遇到的高频问题，每个回答均基于前 9 份设计文档中的技术决策，给出原理、方案和权衡。

---

## 架构设计

### Q1：为什么用微服务而不是单体架构？

这个系统的业务边界天然适合拆分。试卷创建、答题提交、数据统计、用户管理、全文检索是五组独立的业务域，各自有不同的读写特征和负载压力——答题是高频写入、统计是计算密集型、检索是读密集型。如果放在一个单体里，答题高峰期的写入压力会拖慢统计查询，统计的大表扫描会拖慢检索。

拆成微服务后，试卷服务和答题服务可以独立部署和扩容。答题高峰时只扩容 answer-service，不影响其他模块。另外 `paper-service` 和 `answer-service` 之间通过 Kafka 解耦，试卷发布不需要等待答题记录批量生成，这是微服务 + 消息队列的组合优势。

微服务的成本我们也考虑到了——通过 exam-common 公共模块统一工具类和异常处理，通过 OpenFeign 声明式调用降低开发复杂度。

参考：[03-architecture.md](03-architecture.md) 第 2 节

---

### Q2：服务拆分的粒度是怎么决定的？为什么 paper-service 和 answer-service 要分开？

它们虽然都围绕"试卷"这个业务概念，但拆分的依据是**数据归属和写入模式不同**。

paper-service 管理的是试卷元数据（paper、question、option 表），写入频率低（一个校长一天发几张试卷），读频率高（所有老师进试卷时要读）。

answer-service 管理的是答题运行时数据（response、answer 表 + Redis 中转），写入频率极高（10 万老师答题，每秒数千次写入），读频率也高。

如果不拆分：paper 表的一次 ALTER 或慢查询会阻塞 answer 表的写入；answer 表的批量落库会占用连接池，影响 paper 的正常查询。拆分后各自有独立的数据库连接池和缓存策略，互不干扰。

参考：[03-architecture.md](03-architecture.md) 第 2 节

### Q3：为什么选 Kafka 而不是 RabbitMQ 或 RocketMQ？

三个核心原因：

一是**吞吐量**。本系统的核心场景是校长给 1 万+ 老师发卷，瞬间产生 1 万条消息。Kafka 的批量发送 + 分区并行消费可以轻松支撑，RabbitMQ 在这个量级下需要更多集群节点才能达到同等吞吐。

二是**消息持久化**。Kafka 消息写磁盘后按时间保留（默认 7 天），消费者挂了 2 小时后重启，仍可从上次 Offset 继续消费。整个分发链路中试卷消息不会因为消费者短暂不可用而丢失。

三是**分区有序性**。同一 paperId 的消息进入同一分区，保证同试卷的分发消息被顺序处理，避免"先发的老师反而后收到试卷"的问题。

参考：[03-architecture.md](03-architecture.md) 第 5 节，[06-reliability-design.md](06-reliability-design.md) 第 1 节

### Q4：为什么用 Redis 做答题数据中转，而不是直接写 MySQL？

答题是系统中写入频率最高的场景——10 万老师同时答题，每道题一次提交，每秒数千次。直接写 MySQL 在这个量级下延迟会到 5-20ms，老师点"下一题"时会有明显卡顿。

Redis 单次写入 <1ms，差两个数量级。每道题先写 Redis，前端立即返回，老师感知不到延迟。落库 MySQL 的工作交给 5 秒定时任务批量执行，把"高频随机写入"转化成"低频批量写入"。

代价是需要设计一套完整的数据安全保障机制（状态标记 + 重试 + 本地降级 + 对账），这套机制在 06 号文档中已完整设计。

参考：[06-reliability-design.md](06-reliability-design.md) 第 2、3 节

### Q5：为什么用 Canal 同步 ES，而不是应用层双写？

应用层双写（改完 MySQL 顺便写 ES）有三个问题：

**一致性问题**：MySQL 写入成功但 ES 写入失败，需要自己处理补偿逻辑。如果 MySQL 事务回滚了但 ES 已经写了，数据就脏了。

**耦合问题**：每个涉及 ES 索引的操作（新增试题、修改试题、删除试题）都要加一段 ES 同步代码，散落在各个 Service 里，漏写的概率很高。

**遗漏问题**：如果有人直接操作数据库（运维修数据、后台脚本），ES 不会收到通知。

Canal 监听 binlog 是旁路方案——MySQL 变更后由 binlog 驱动，与业务代码解耦。即使有人直接改库，ES 也能同步。同步失败时 Canal 会自动重试，且有每小时的对账任务兜底。

参考：[09-es-design.md](09-es-design.md) 第 3 节

### Q6：为什么要设计三级缓存，两级不行吗？

只有 Caffeine + MySQL（两级）：Caffeine 是 JVM 内存，多个服务实例各自存一份。实例 A 更新了数据库并清理了自己的 Caffeine，实例 B 的 Caffeine 里还是旧数据——造成多实例间的缓存不一致。60 秒 TTL 意味着最多 60 秒窗口的不一致，对有些场景可接受，但对需要即时生效的配置变更不够好。

只有 Redis + MySQL（两级）：Redis 是共享的，没有多实例不一致问题。但 Redis 的网络往返（即使内网）也有 1-3ms，对"老师进入试卷时要加载 30 道题"这种场景，每毫秒都很关键，Caffeine 的本地内存读取几乎是零延迟。

三级的好处是：热点数据走 Caffeine（<1ms）→ 次热点走 Redis（<5ms）→ 冷数据走 MySQL。99% 的请求都由前两级兜住，MySQL 压力降到最低。

参考：[07-cache-design.md](07-cache-design.md) 第 1、3 节

### Q7：为什么试卷分发是异步的？同步等待不是更简单吗？

同步模式下，校长点"发布"→ 后端循环 INSERT 1 万条 response → 返回"发布成功"。1 万次 INSERT 即使批量优化也要数秒到数十秒，校长要盯着转圈等。这个体验不可接受。

异步模式：校长点"发布"→ 后端校验 + 发 Kafka 消息 → 200ms 内返回"分发中"→ Kafka 异步消费 → 批量写 response。校长的等待时间从数十秒降到 200ms。

代价是多了"分发中"这个中间状态，需要在前端展示分发进度（WebSocket 或轮询）。这个代价远小于用户体验的损失。

参考：[03-architecture.md](03-architecture.md) 第 5 节，[04-features.md](04-features.md) 第 2 节

### Q8：response 表为什么冗余存了省市区校？这不是违反三范式吗？

是违反了，但这是有意识的冗余，原因有三：

**查询效率**：区域统计（按市分组算平均分）需要省市区校字段。如果不冗余，每次统计都要 JOIN user 表——response 40 万条 JOIN user 40 万条，查询会很重。

**数据快照**：冗余存的是"答题时的层级"，不是"当前的层级"。如果老师从郑州调到了洛阳，历史试卷记录应该归属于郑州还是洛阳？冗余字段保存了答题时的真实归属，不受后续人事变动影响。

**分层统计独立性**：统计服务可以直接基于 response 表完成所有区域维度的聚合，不需要调用 user-service（服务解耦）。

权衡：INSERT 时多写 4 个字段，查询时避免一次 JOIN。对于写入频率远低于查询频率的 response 表（写入一次，查询无数次），这个取舍是划算的。

参考：[02-database-design.md](02-database-design.md) 第 2.4 节

## 数据安全与可靠性

### Q9：Kafka 消息丢了怎么办？能保证 100% 不丢吗？

技术上不可能保证"绝对"100%，但可以从三个层面把概率降到极低：

**生产端**：`acks=all`（等所有 ISR 副本确认）+ `enable.idempotence=true`（防重试导致重复）。如果 Kafka 集群全挂了，消息写入服务器本地文件，等恢复后重新发送。

**Broker 端**：3 副本 + `min.insync.replicas=2` + `unclean.leader.election.enable=false`（不允许脏副本当 Leader）。只要不同时坏 2 个以上副本，消息就不会丢。

**消费端**：手动提交 Offset——只有 MySQL 写入成功后才提交。如果写入失败，不提交 Offset，消息被重新消费。

三重保障下，消息丢失的概率已经低于服务器硬件同时多点故障的概率。最后的兜底是每日对账——发现 paper ↔ response 数量对不上，人工补齐。

参考：[06-reliability-design.md](06-reliability-design.md) 第 1.1、1.2 节

### Q10：答题过程中电脑突然断电，老师的答案会丢吗？

不会。三层保护从快到慢覆盖这个场景：

**第一层（Redis）**：每 3 秒自动保存一次进度到 Redis（`answer:progress:{responseId}`），每道题的答案也实时写入 Redis。断电时，最多丢失 3 秒内的未保存数据。

**第二层（前端 localStorage）**：每道题选择答案时立即写入浏览器本地存储。断电后重新打开页面，localStorage 中标记为 `synced: false` 的答案会自动重发到后端。

**第三层（服务器本地文件）**：如果断电时 Redis 也不可用，答案被写入服务器的本地降级文件（`/data/answer-fallback/`），Redis 恢复后自动回补。

恢复流程：老师重新登录 → 系统检测到 `answer:progress:{responseId}` 存在 → 恢复到断电前的题目位置 → 已保存的答案自动填充 → 倒计时恢复到剩余时间 → 继续答题。

参考：[06-reliability-design.md](06-reliability-design.md) 第 3.2、3.6b 节

### Q11：5 秒定时任务正在落库，老师同时点了提交试卷，会冲突吗？

有两种情况：

**情况一**：5 秒定时任务在做批量落库（写 answer 表），用户点提交触发了 `forceFlushForResponse`（也写 answer 表）。此时用 Redisson 分布式锁（`lock:answer:flush:{responseId}`）保护，后到的一边等待锁释放。

**情况二**：3 秒定时保存和用户点"下一题"同时写 Redis（`answer:single:{responseId}:{questionId}`）。此时不用锁——Redis 单线程，后到的覆盖先到的。真正的风险是旧请求因网络延迟后到达反而覆盖新数据——解决方案是前端每条请求带客户端时间戳，后端只接受比已有数据时间戳更新的请求。

参考：[06-reliability-design.md](06-reliability-design.md) 第 3.7 节

### Q12：Redis 中待落库的数据，5 秒定时任务崩溃了怎么办？

不会丢。关键在于**不用 RPOP，用 Range**。

RPOP 是破坏性读取——取出来的同时从 Redis 删除。如果在取出来之后、写 MySQL 之前崩溃，这 500 条从 Redis 和 MySQL 两端都消失。

Range 只读不删。流程是：Range 取前 500 条 → 标记为 processing → 写 MySQL → 成功后 LREM 删除 + 删 data key。如果在写 MySQL 前崩溃，processing 标记随 Redis 过期（5 分钟）自动恢复为未处理状态，数据 key 还在，下一轮定时任务或补偿任务会重新处理。

参考：[06-reliability-design.md](06-reliability-design.md) 第 3.4 节

---

### Q13：为什么落库失败的重试不用指数退避？

指数退避（1s → 2s → 4s → 8s）适用于对端是外部系统、需要避免把对方打崩的场景（如 HTTP 重试远程 API）。

本系统的重试两端都在自己机房（Redis 和 MySQL 都是本地），不存在"打崩"问题。用固定间隔（5 秒定时 + 60 秒补偿）能让失败数据以最快速度恢复。退避反而会让数据越等越久——这对答题数据落库这个场景来说是不可取的。

唯一可能需要退避的情况是 MySQL 连接池被打满，但本系统已给落库任务配置了独立连接池，与在线业务隔离，这个风险已消除。

参考：[06-reliability-design.md](06-reliability-design.md) 第 3.4 节末尾

### Q14：Kafka 的死信队列和 Redis 落库失败的"死信"是一回事吗？

不是。两者是完全独立的机制：

Kafka 死信队列（`paper_distribute.DLQ`）是一个真正的 Kafka Topic，解决的是消息消费阻塞问题——某条消息反复处理失败，丢弃它会阻塞整个分区，把它移到死信 Topic，主队列继续前进。死信消息需要人工排查原因，修好后重新投递。

Redis 落库失败的"死信"是指定时任务将某条答题数据重试了 5 次仍无法写入 MySQL，就把这条数据的信息存入数据库死信表（`dead_letter_record`），发告警让人介入。它解决的是单条数据持久化失败的兜底问题。

两者各管各的：Kafka 死信管"消息分发"链路，Redis 死信管"数据落库"链路，互不相干。

参考：[06-reliability-design.md](06-reliability-design.md) 第 1.5 节末尾

### Q15：每日对账发现数据不一致怎么办？

分三道对账，每道的处理策略不同：

第一道对账（paper ↔ response 人数对不上）：差几十人→自动补齐 response 记录；差几千人或 paper 已截止→发红色告警，人工判断是重新开放试卷还是作废。

第二道对账（answer 少了题）：先查 Redis 还有没有数据→有就自动 forceFlush；没有就查服务器降级文件→有就恢复；都没有→确认丢失，丢几题标记"数据缺失"仍可批阅，丢整张直接联系老师重答。

第三道对账（分数对不上）：以明细（answer 表的 SUM）为准，自动覆盖汇总（response.score），记下修正前 vs 修正后的值供追溯。

共性规则：差异 <10 条仅记日志不告警；10-100 条黄色预警；100 条以上红色紧急告警。连续 3 天同类差异→触发深度对账。

参考：[06-reliability-design.md](06-reliability-design.md) 第 5、6 节

## 缓存

### Q16：更新了数据库后，缓存里的数据还是旧的，怎么保证一致性？

采用"先更新 DB，后删除缓存"策略（Cache Aside Pattern），不是更新缓存。

为什么要删而不是更新：同时更新 DB 和缓存在并发下可能出现写覆盖——A 更新 DB → B 更新 DB → B 更新缓存 → A 更新缓存（A 的旧数据覆盖了 B 的新数据）。删除不会有这个问题——谁读到旧数据谁承担正确性风险，而下一次查询会因为缓存缺失而重新从 DB 加载。

关于 Caffeine 本地缓存的多实例一致性问题：每个实例的 Caffeine 独立，A 实例更新了 DB 并删了 Redis，B 实例的 Caffeine 可能还缓存着旧数据。但因为 TTL 只设了 60 秒，最多 60 秒后自然过期。对于试卷修改这种低频操作，60 秒窗口可接受。未来如需强一致，可以通过 Redis Pub/Sub 广播缓存失效通知。

参考：[07-cache-design.md](07-cache-design.md) 第 3.4 节

---

### Q17：布隆过滤器怎么防止缓存穿透？误判了怎么办？

布隆过滤器在启动时加载所有有效的 paperId。查询时先过布隆过滤器：

- 布隆说"不存在"→ 一定不存在，直接返回 null，不查 DB
- 布隆说"可能存在"→ 可能有（概率 99%）也可能误判（概率 1%）

对那 1% 的误判（布隆说存在但 DB 实际不存在），补充一个短 TTL 空值缓存：查 DB 发现不存在后，写一条 `paper:info:{paperId} = "NULL"`，TTL 30 秒。30 秒内的重复查询直接返回 null，不走 DB。

新试卷发布时，布隆过滤器同步添加（`filter.put(paperId)`），保证新试卷能被查到。

参考：[07-cache-design.md](07-cache-design.md) 第 3.1 节

### Q18：为什么有的数据放三级缓存，有的只放一级或两级？

判断标准是四个维度：访问频率、数据量大小、多实例是否需要共享、实时性要求。

老师试卷列表（`teacher:papers:{userId}`）：访问频率高但每人不同，放 Caffeine 会被大量不同 userId 的 key 撑满 LRU 池，命中率极低——所以只放 Redis（L2），不放 Caffeine。

权限配置（`config:project:{projectId}`）：数据量可能大，但项目级的配置所有用户共享——所以放 Redis（L2），不放 Caffeine。

试卷信息（`paper:info:{paperId}`）：访问频率高、热点集中、多实例共享、允许 60 秒延迟——所以 Caffeine + Redis + MySQL 三级全上。

参考：[07-cache-design.md](07-cache-design.md) 第 2、4 节

## 性能与优化

### Q19：10 万老师同时答题，系统怎么撑住？

压力最大的三个环节各有方案：

**答题写入**：Redis 做中转，每道题答案写 Redis <1ms。不直接写 MySQL。MySQL 只承受 5 秒一次的批量写入（500 条/批），压力从"每秒数万次单条写入"降到"每秒 100 次批量写入"。

**试卷查询**：三级缓存（Caffeine → Redis → MySQL），热点试卷在 Caffeine 本地内存命中，不需要走网络。

**提交试卷**：提交接口主动触发 `forceFlushForResponse`，确保该老师的答案全量落库后再做自动批阅。用分布式锁避免与定时任务冲突。

**限流**：Sentinel 对核心接口限流，每个老师每分钟最多查 100 次，防止恶意或异常请求。

参考：[03-architecture.md](03-architecture.md) 第 4-6 节，[07-cache-design.md](07-cache-design.md)

### Q20：ES 搜索为什么能比 MySQL LIKE 快那么多？

MySQL 的 `LIKE '%keyword%'` 是全文扫描——遍历所有行、逐行匹配字符串。100 万试题，每次查询扫 100 万行，且前后通配符无法利用 B+Tree 索引（最左前缀原则）。

ES 用的是**倒排索引**。以 IK 分词器把"一元二次方程解法"分词为"一元"、"二次"、"方程"、"解法"，建立"词 → 文档 ID 列表"的倒排表。查询"方程"时，直接从倒排表取出包含"方程"的所有文档 ID，数据量从 100 万缩减到几千。

再加上 Filter Context 的自动缓存（筛选条件如题型=选择、难度=简单的结果被缓存），重复查询几乎零开销。最终从 MySQL 的 2 秒级降到 50ms 以内。

参考：[09-es-design.md](09-es-design.md) 第 4 节

### Q21：响应时间的目标是多少？哪些地方可以接受延迟？

| 操作 | 目标延迟 | 可接受延迟上限 | 是否可异步 |
|------|:---:|:---:|:---:|
| 老师提交单题答案 | <50ms | 200ms | 否（感知） |
| 试卷列表查询 | <100ms | 300ms | 否 |
| 试卷发布（校长点发布按钮） | <200ms | 500ms | 分发过程异步 |
| 统计数据查询 | <500ms | 2s | 可预计算+缓存 |
| ES 试题搜索 | <50ms | 200ms | 否 |
| 每日对账 | 非在线，无关 | 30 分钟 | 本身就是异步 |

核心原则：**用户直接操作的接口必须在 200ms 内返回**。200ms 是用户感知"卡顿"的阈值。超过这个时间的（如试卷分发、数据统计），通过异步化或缓存预计算来规避。

## 数据设计

### Q22：为什么用雪花算法生成 ID，而不是数据库自增？

分布式微服务架构下，多个服务实例各自独立写入数据库。用自增 ID 会遇到两个问题：

一是**冲突**：answer-service 部署了 3 个实例，如果用自增 ID，3 个实例同时 INSERT 可能产生重复 ID（除非用分布式自增方案，那又引入了额外复杂度）。

二是**暴露业务量**：自增 ID 让外部可以推测系统的试卷量、答题量。

雪花算法在应用层生成 64 位 Long，包含时间戳 + 机器 ID + 序列号，全局唯一、趋势递增（利于 MySQL 索引）、不依赖数据库。Hutool 的 `IdUtil.getSnowflake()` 一行代码即可集成。

参考：[02-database-design.md](02-database-design.md) 第 5 节

---

### Q23：paper 表里的 `question_count` 为什么是冗余字段？可以直接 COUNT question 表呀。

冗余它是为了避免每次展示试卷列表时都做一次子查询或 JOIN，同时也是数据对账的依据。

每次展示试卷列表时 SELECT paper.* 就能直接拿到题目数量，不需要 COUNT question 表。虽然写入时需要同步维护（添加/删除题目时 update question_count），但试卷的写入频率远低于读取频率，以写换读是划算的。

另外，每日对账时用 paper.question_count 作为期望值去对比 question 表的实际行数——如果对不上，说明题目数据出了问题。

参考：[02-database-design.md](02-database-design.md) 第 2.1 节，[08-statistics-optimization.md](08-statistics-optimization.md) 第 2.3 节

---

### Q24：option 表里为什么冗余 paper_id？

查询频率最高的场景是老师进入试卷答题页，需要一次查出该试卷的所有题目和所有选项：

```sql
SELECT * FROM question WHERE paper_id = ?;
SELECT * FROM option WHERE paper_id = ?;
```

如果 option 表只有 question_id 索引，查选项就需要先查出 question_id 列表再做 IN 查询，多一次回表。冗余 paper_id 后，一张试卷所有选项一次索引扫描即可全部取出。

代价是多了 8 字节的外键字段和一条索引。对于 option 表这种"写一次读无数次"的场景，这个代价完全值得。

参考：[02-database-design.md](02-database-design.md) 第 2.3 节

## 业务逻辑

### Q25：新增老师为什么看不到已有的试卷？怎么处理？

校长发试卷时选了 100 个老师，response 表插入 100 条记录。后来项目新增了 50 个老师，这 50 人的 response 表中没有记录，看不到试卷。

处理方式叫"数据补偿"：老师点"试题"菜单时，系统先查 response 表。如果某张已发布试卷在 response 中没有该老师的记录，系统按层级判断（该老师的省市区校是否在试卷的目标范围内），符合条件则自动补插一条 response 记录。

补偿不是批量而是按需的——只有老师主动进入试题模块时才触发。这样做的好处是避免半夜跑全量补偿任务，而且新增老师如果不进试题就不产生无效记录。

参考：[04-features.md](04-features.md) 第 2.5 节

---

### Q26：主观题和客观题的批阅流程有什么不同？

客观题（选择、判断）：老师提交试卷时自动批阅。后端比对 answer.answer_content 和 option.is_correct，匹配则得分。不需要校长介入。

主观题（简答）：老师提交后 answer.score 为 null。校长进入批阅页面，逐题查看作答内容，手动输入分数和评语。所有题目批完后，确认批阅完成，系统汇总各题分数写入 response，判定合格与否。

如果 config 表配置了"主观题自动给分"——比如某些简单考核不需要人工批阅——系统会给所有提交的主观题自动给满分，简化为全自动流程。

参考：[04-features.md](04-features.md) 第 2.3、2.4 节

---

### Q27：怎么防止老师超时答题？

**倒计时在前端**：试卷有 `duration_minutes` 字段，前端启动倒计时。归零时自动触发提交接口，关闭答题页面。

**后端双重校验**：提交接口中比对当前时间和 response 的答题开始时间，超过规定时长则拒绝接受新答案。防止前端倒计时被篡改。

**断网场景**：老师断网时倒计时仍在跑——但 Redis 中的进度保存了 `remainingSeconds`，恢复答题时倒计时恢复为断网前的剩余时间，不是重新计时。

参考：[04-features.md](04-features.md) 第 2.3 节

---

### Q28：项目制的权限是怎么控制的？为什么不是简单的角色判断？

系统面向全国不同省份、不同需求定制。有的省份要求老师只能答题不能发文章，有的省份要求校长既能发试卷也能发文章。

如果用硬编码的角色判断（`if (role == PRINCIPAL)`），每个省份的需求变化都要改代码、重新部署。

项目制方案：用 config 表和 permission 表把"谁能用什么工具、有什么按钮权限"做成配置数据。管理员在后台给每个项目配置即可，不改代码。权限判断逻辑通用——查表、返回有权限的功能列表、前端按列表渲染菜单。

参考：[04-features.md](04-features.md) 第 1、5 节

## 部署与运维

### Q29：本地开发环境怎么搭建？

```bash
# 1. 启动所有中间件
docker-compose up -d
# 自动启动 MySQL(3306)、Redis(6379)、Kafka(9092)、ES(9200)

# 2. 初始化数据库
mysql -u root -p < docs/sql/init.sql

# 3. IDEA 中按顺序启动微服务
# exam-gateway → exam-common → exam-user-service → exam-paper-service
# → exam-answer-service → exam-statistics-service → exam-search-service
```

中间件通过 Docker Compose 统一管理，不要求开发者的电脑上安装 MySQL/Redis/Kafka/ES。

参考：[01-tech-stack.md](01-tech-stack.md) 第 8 节

---

### Q30：怎么保证部署和线上环境一致？

所有中间件的版本和配置在 `docker-compose.yml` 中锁定，与生产环境保持一致（生产环境可能用 K8s + Helm，但镜像版本和配置参数相同）。

每个微服务有独立的 `Dockerfile`，CI/CD 构建镜像后推送到镜像仓库。多环境通过环境变量（`application-{env}.yml`）区分，不修改代码。

参考：[03-architecture.md](03-architecture.md) 第 8 节
